## 3. Derived facts

- **SpeedType index table (0x81da58), all 8 entries VERIFIED (tool output):** 0 Foot, 1 Track, 2 Wheel, 3 Hover,
  4 Winged, 5 Float, 6 Amphibious, 7 FloatBeach. This matches the ground-table column order of AP-15, and the
  "constant 1.0" column (index 4) is the `Winged` column.
- **Fly ILocomotion slot +0x84 = FUN_004cfe20**, if 0x7e89f4 is the Fly ILocomotion vtable (YRpp ILocoVTable,
  REFERENCE-SUGGESTED). The routine is `__stdcall` with the interface pointer `p` as its only argument:
  `return F2I((double)(int)GetType(p[+0x8])[+0x678] * *(double*)(p + 0x44))`, where `[+0x8]` is LinkedTo and
  slot +0x84 of LinkedTo's vtable is the type getter that row 15 also uses.
  FUN_004cd600 calls this slot on `this+0x4` (spec row 28), so `p = this + 4`. Therefore `p+0x8` = `this+0xC` (LinkedTo,
  same offset the Jumpjet locomotor uses) and `p+0x44` = `this+0x48`. This is the speed ratio that FUN_004cd600 steps by 0.1
  toward `+0x40 = min(1, dist / Type+0x2f8)`.
  **Fly speed per frame = F2I(Type.Speed(+0x678) * Loco+0x48)**, truncated (F2I). The `p = this + 4` step is
  derived from two outputs (ev_e8f8f023..., ev_b43b822b...) and is not itself one tool output.
- 0x4ce4b0 (Phobos hook neighbourhood) is not decodable in the Ghidra listing and is not the slot target.
- **0x6f3270** is a one-instruction-entry routine (`MOV EAX,[ECX]` ...) referenced only as data from six table
  addresses (0x7e2328, 0x7e3f40, 0x7e8d18, 0x7eb0dc, 0x7f49e4, 0x7f5cf4). That pattern fits a shared virtual
  method; Ghidra created no procedure (auto-analysis gap). The containing procedure question is answered: there is none.
- **FUN_007caf30 = `strchr(s, c)`**. FUN_005283d0 calls it as `FUN_007caf30(value, 0x2525)`; the `char` argument is
  the low byte, 0x25 = `'%'`. So an INI double is multiplied by [0x7e3808] (0.01) only when the value string contains
  `%`. `[Land]` values such as `Foot=100%` are scaled; `Foot=1.0` is not (derived from ev_703c6bb6... + ev_be4c09eb...).
- **FUN_004b4780 = Drive track point transform.** Flags = dword at `0x7e7b30 + TrackNumber*12`, i.e. word +8 of the
  12-byte DAT_007e7b28 entry. Input point (x, y) and facing f (byte):
  - bit 0 swaps x and y and sets f = (-0x40 - f) & 0xff;
  - bit 1 negates x and sets f = -f & 0xff;
  - bit 2 negates y and sets f = (-0x80 - f) & 0xff.

  The output point is `(Loco+0x40 + x, Loco+0x44 + y)`. Track points are therefore offsets in the same unit as
  the coordinates stored at +0x40/+0x44 (the `>> 8` cell conversion makes that leptons, 256 per cell, still
  inferred from use). The third dword of a track point is a facing byte 0..255 (bits 0-7 kept by `AND 0xff`).
- **FLDCW census (partial):** no `FLDCW word ptr [abs32]` exists at an instruction boundary in `.text`
  (runs 10-14). F2I itself uses `FLDCW word ptr [ESP]` (AP-14). Register-based forms (`d9 /5` with other ModRM)
  are not enumerated: the masked byte search (run 15) cannot tell instruction starts from operand bytes. Whether
  other code changes the x87 control word therefore stays UNVERIFIED.
