## 3. Derived facts

From the quotes above only:

1. FUN_007c5f00 spans 0x7c5f00-0x7c5f3c and takes its input on the x87 stack (`in_ST0`, `float10`); it has no memory argument and no callees.
2. It stores the current x87 control word (`FNSTCW [ESP]`, 0x7c5f03), masks it to 16 bits (`AND EDX,0xffff`) and compares it with the 32-bit data value at `0x00822d80` (0x7c5f13).
   - If equal: `FISTP qword ptr [EAX]` (0x7c5f1b) converts ST0 to a 64-bit integer with the control word as it is.
   - If different: the value of `[0x00822d80]` is loaded into the control word (`MOV [ESP],EDX`; `FLDCW word ptr [ESP]`, 0x7c5f2f) and then `FISTP qword ptr [EAX]` (0x7c5f32).
3. The result is returned as a 64-bit integer in EDX:EAX (`MOV EDX,[EAX+4]`; `MOV EAX,[EAX]`). Callers that use only EAX (e.g. 0x4db1a0, ev_d12530ff) take the low 32 bits.
4. There is exactly one `FLDCW` (0x7c5f2f) and no restore of the caller's control word before either `RET`: after a call that took the 0x7c5f26 path, the control word remains equal to `DAT_00822d80`. On every exit the conversion therefore happens with the control word equal to `DAT_00822d80`.

The rounding mode is bits 10-11 of the 16-bit value stored at `DAT_00822d80`. **That value is not contained in any tool output of this package** (the function output names it only as `DAT_00822d80`; the p-code carries `constant_hex: null` for it).
