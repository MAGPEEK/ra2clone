## 3. Derived facts (from the quotes only)

1. Hook address 0x4CDA78 lies inside **FUN_004cd600** (0x4cd600-0x4ce4a9; `this` in ECX -> ESI at 0x4cd60c; single caller 0x4ccbbf, UNCONDITIONAL_CALL). The six bytes at 0x4cda78 are `TEST EAX, EAX` (2) + `MOV dword ptr [ESP + 0x18], EAX` (4) - the instructions a 6-byte hook there replaces - and EAX at that point is the return value of `0x4cda72: CALL dword ptr [EAX + 0x84]` with `EAX = [EDI]` and EDI pushed as the argument.
2. EDI at 0x4cda72 is `ESI + 0x4` (`0x4cd682: LEA EDI, [ESI + 0x4]`; no EDI write on the paths from there to 0x4cda08, section 2.2). So the speed value is obtained by a **stdcall-style virtual call through the locomotor's second vtable (`this+0x4`) at slot +0x84**, with `this+0x4` as the interface pointer. This is not the TechnoClass vtable slot +0x84 used at 0x4cda1b (there the object is `[ESI + 0xc]`), and it is not a direct read of Type+0x678: no `0x678` and no `0x38c` operand occurs in FUN_004cd600. **Type+0x678 is therefore not read in this function**; whatever the slot +0x84 routine returns is used as the frame's integer speed.
3. The frame's speed `iVar7` (int in EAX, stored at `[ESP + 0x18]`) gates the move: `JLE 0x004cdb4c` skips the position step when it is <= 0 (pseudocode `if (0 < iVar7)`).
