## 3. Derived facts

From 2.1:
- The code at 0x70efe0 is a complete 22-byte routine with two exits: it loads the vtable pointer of `this` (ECX) (`MOV EAX,[ECX]`), calls the virtual at vtable slot +0x84 (`CALL [EAX+0x84]`), and if the returned EAX is non-zero returns the dword at `EAX+0x678` (`MOV EAX,[EAX+0x678]; RET` at 0x70efec/0x70eff2); if the call returned 0 it jumps to 0x70eff3 and returns 0 (`XOR EAX,EAX; RET`).
- The value returned is therefore `[(vtable+0x84)()] + 0x678` read as a 32-bit dword in EAX, or 0 when that call yields a null pointer. That slot +0x84 returns the TechnoType (and so +0x678 is TechnoTypeClass+0x678, the scaled `Speed=` of row 3) is consistent with the call-site comment in Rule B and with the same `CALL dword ptr [EAX + 0x84]` at 0x4db1a9 in ev_d12530ff, but the target of slot +0x84 is not shown by any output here (that is AP-13 / AP-27 FUN_006f3270). Marked: slot +0x84 -> GetTechnoType REFERENCE-SUGGESTED / UNVERIFIED in this package.
- Row #15's claim "`mov eax,[eax+0x678]` at 0x70EFEC" is confirmed verbatim (`8b8078060000`, `MOV EAX,dword ptr [EAX + 0x678]` at 0x70efec).
- The routine takes no stack arguments (`RET` without immediate at both exits) and uses ECX as `this` (thiscall-style). No stack frame, no callee-saved registers touched.
- Ghidra did not define a function at 0x70efe0 (`procedure: null` on all eight decodes; runs 1/3/5 errors), so there is no `FUN_0070efe0` symbol in the snapshot; the spec's helper name "FUN_0070EFE0" is a label chosen by the spec, not a Ghidra symbol.
