## 3. Derived facts

From the quotes above only:

1. FUN_00521d80 spans 0x521d80-0x521dc8 (73 bytes). `this` arrives in ECX and is kept in ESI (`MOV ESI, ECX`, 0x521d81). Its only call is `CALL 0x004db1a0` at 0x521d83 (kind `UNCONDITIONAL_CALL`); the return value is moved to ECX at 0x521d88 and is the running speed value `v` for the rest of the routine. This confirms the byte-read part of Evidence row 20 ("calls 0x4DB1A0 at 0x521D83").
2. At 0x521d8a-0x521d92 the routine tests the byte field `this+0x6DB`; if it is zero it jumps to 0x521dc5 and returns `v` unchanged (`MOV EAX, ECX; POP ESI; RET`). So the multiplier is only applied when `this+0x6DB != 0`.
3. At 0x521d94 the instruction is `MOV EAX, dword ptr [ESI + 0x6c0]` (confirms the byte read in row 20). It loads the pointer at `this+0x6C0`; at 0x521d9a the byte at `[that pointer]+0xEBD` is tested (`MOV DL, byte ptr [EAX + 0xebd]; TEST DL, DL`). The test reads a byte of the object `this+0x6C0` points to, at offset 0xEBD, and compares it with zero.
4. Branch `[+0x6C0]+0xEBD != 0` (0x521da4-0x521dbb): `v` is multiplied by the immediate `0x55555555` (`IMUL ECX`, 64-bit signed product), the high dword minus `v` is shifted right by 1 with a sign-bit correction (`SHR EAX, 0x1f; ADD EDX, EAX`) and added to `v`. The pseudocode renders this as `iVar2 = hi32(iVar1 * 0x55555555) - iVar1; return iVar1 + ((iVar2 >> 1) - (iVar2 >> 0x1f))`. Evaluating that quoted formula for every integer -255..255 (my arithmetic on the quoted expression, 32-bit signed semantics) gives exactly `v - trunc(v/3)`, i.e. `v` reduced by a third with the third truncated toward zero: 0->0, 1->1, 2->2, 3->2, 4->3, 5->4, 6->4, 9->6, 10->7, 12->8, 100->67, 255->170. This is the compiler's magic-number idiom for a signed division by -3 (interpretation); the operands `0x55555555` and the shift `1` are immediates in the code, not loaded from any data address.
5. Branch `[+0x6C0]+0xEBD == 0` (0x521dbc-0x521dc5): `MOV EAX, ECX; CDQ; SUB EAX, EDX; SAR EAX, 0x1; ADD ECX, EAX` = `v + trunc(v/2)` (pseudocode: `iVar1 = iVar1 + iVar1 / 2`), i.e. 1.5x with the half truncated toward zero: 1->1, 2->3, 3->4, 5->7, 10->15, 255->382.
6. The whole routine is integer-only: no x87 instruction, no `FLD`/`FMUL`, no `DAT_` operand, no `CALL 0x007c5f00`. The "prone multiplier" is therefore **not** a double constant in .rdata and **not** read from a rules key inside this function; it is the pair of immediate integer operations above. The spec's wording "(constant at 0x521D94, see raw bytes in evidence folder)" is wrong in both halves: 0x521D94 holds a field load, not a constant, and the multiplier has no byte-level constant to show. Whether the two tested fields (`this+0x6DB`, `[this+0x6C0]+0xEBD`) are themselves set from rules keys elsewhere is outside this output (UNVERIFIED; the field names below are reference-suggested only).
7. Result type: the return is a 32-bit int in EAX on all three paths (0x521db9, 0x521dc5). No rounding routine is involved, so AP-14's open F2I rounding mode does not affect this function.
8. Run 2: the only reference to 0x521d80 in the whole program is from `0x7eb590`. `0x7eb590 - 0x538 = 0x7eb058`, the address the spec's row 18 names as the InfantryClass vtable (byte read). The xrefs output confirms a single reference at exactly vtable-base + 0x538; it does not itself expose the reference kind or that 0x7eb058 is a vtable (that remains the row-18 byte read / YRpp inference). No code caller exists, consistent with a virtual-only `GetCurrentSpeed`.
9. Phobos consistency (not evidence, but a cross-check of the quoted addresses): the Phobos hook at 0x521D94 with size 6 covers exactly the 6-byte instruction `MOV EAX, dword ptr [ESI + 0x6c0]` (0x521d94-0x521d99), takes `currentSpeed` from ECX (set at 0x521d88) and returns to 0x521DC5, which is the quoted `MOV EAX, ECX` exit.
