# Review: T-022-AP-implementation.md against docs/specs/T-022-movement-speed.md

Reviewed: `docs/arbeitspakete/T-022-AP-implementation.md` (AP-01..AP-07) vs `docs/specs/T-022-movement-speed.md` (DRAFT, 2026-10-26).
Scope: behavioural claims, constants/offsets, test values (recomputed from the spec rule text and checked in IEEE-754 double where the package prescribes doubles), dependencies, project rules, coverage.

Severity: high = implementation would not reproduce the spec or a test as written is wrong; medium = unverified material presented as fact, mismatch in design/dependency that will surface during implementation; low = wording, provenance or minor gap.

## Findings

| AP | Finding | Severity | Suggested fix |
|---|---|---|---|
| AP-01 | The file-header rationale states "`255 * 1.2` is `305.999...`; round-to-nearest gives 306 but truncation gives 305". In IEEE-754 double (what AP-01 prescribes: SSE2, no FMA) the product `255.0 * 1.2` rounds to exactly `306.0`, so truncation also gives 306. The example is false for the chosen representation, and the test `F2I(255 * 1.2) == 306` "with the literal double product" therefore does not discriminate rounding modes at all (it is tagged `F2I-UNVERIFIED` for no reason). | high | Use an example whose double product is genuinely non-integral (e.g. `10 * 0.75 = 7.5`, or `7 * 1.1 = 7.700000000000001`) and drop or relabel the 255*1.2 test as mode-independent. |
| AP-01 / AP-04 | The game evaluates `FILD max; FMUL mult; FMUL SpeedMultiplier; CALL F2I` on the x87 stack (80-bit extended intermediates; spec raw asm 0x4db1cd-0x4db1db). There the product 255*1.2 really is 305.99999999999998867 before F2I, so under truncation semantics the game would return 305 while the .NET double port returns 306. AP-01 claims "determinism" via SSE2 doubles (true) but presents this as sufficient; neither the spec nor the package mentions extended precision. The whole "swappable rounding seam" is incomplete if only the final F2I mode is switchable but the intermediate precision is not. | high | Document in AP-01 that the game's intermediate is x87 extended, add this to the spec's open questions, and make the seam cover the product as well (e.g. `MulRound` operating on `decimal`/rational or an explicit "extended-precision emulation" strategy) or state explicitly that bit-exactness with the game is not a goal of T-022. |
| AP-07 | Test expectations are decimal, but the package prescribes a `float` table widened to double times a double constant. Recomputed: `(double)(float)0.8 * 0.75 = 0.6000000089406967` (not 0.6); `(double)(float)0.8 * 1.25 = 1.0000000149011612` (not 1.0); `(double)(float)0.8 * 0.5 = 0.4000000059604645` (not 0.4). Even with pure doubles, `0.8 * 0.75 = 0.6000000000000001`. Four of the nine listed tests fail under exact equality. Only `0.0 -> 0.5`, `0.5 * 0.75 = 0.375` and `1.5 -> 1.0` are exact. | high | Either pick table values exactly representable in float (0.5, 0.25, 0.75, 1.0) or compute expectations with the same arithmetic (`(double)(float)x * y`) and compare bitwise; avoid tolerance-based asserts in a determinism-focused sim. |
| AP-04 | Step 1 computes `MulRound(max, countryMult * speedMultiplier)`, i.e. `(mult * SpeedMultiplier)` first, then `* max`. The spec's asm is `(max * mult) * SpeedMultiplier` (0x4db1cd-0x4db1d5). Floating-point multiplication is not associative; the package even says "keep that order" and then does not. Also AP-01 declares that only `MulRound(int, SpeedMultiplier)` is public and forbids implicit conversion, so `countryMult * speedMultiplier` (SpeedMultiplier x SpeedMultiplier) has no defined operator. | medium | Define `MulRound(int v, SpeedMultiplier a, SpeedMultiplier b) = F2I(((double)v * a) * b)` or an equivalent that fixes the left-to-right order; keep the single F2I. |
| AP-07 | The spec marks "which comparison is 'uphill' is inferred from the key names, UNVERIFIED" (Rule D). AP-07 presents `heightThere < heightHere -> Uphill*`, `heightHere < heightThere -> *Downhill` as fact and words the tests semantically ("downhill", "uphill") instead of by height comparison; no tag on the downhill test (only the uphill one gets `UPHILL-KEYS-UNVERIFIED`, and that tag is about key names, not direction). | medium | Express the tests as `heightThere < heightHere` / `heightHere < heightThere` and tag both with a `HILL-DIRECTION-UNVERIFIED` trait; keep the mapping in one place so it can be flipped. |
| AP-07 | Inconsistent treatment of equally UNVERIFIED rules keys: row 16 (`TrackedDownhill`, `WheeledDownhill`, `ConditionYellow`, `VeteranSpeed`) and row 16b (`TrackedUphill`, `WheeledUphill`) are both "byte read: fstp preceded by key push". AP-07 binds the row-16 keys to T-020 INI names but refuses an INI binding for row 16b and invents different placeholder names (`UphillTracked`/`UphillWheeled`, word order reversed vs spec's `TrackedUphill`/`WheeledUphill`). The package basis text also says the uphill names are "UNVERIFIED" as if the spec gave none, but spec row 16b does name them. | medium | Treat all six keys the same way (bind with the spec's names and a `// row 16/16b UNVERIFIED` comment, or bind none); use the spec's spelling `TrackedUphill`/`WheeledUphill`. |
| AP-06 / AP-07 | Spec C.4: the coefficient is "clamped to at least 0.2 (constant 0x7E3548) while crushing (0x4b1150-0x4b1173)". This is part of the VERIFIED-by-tool-output function ev_82818cd0, but no package implements or tests it; AP-06 leaves `// TODO T-022 C.4`, AP-07 lists it as an open point. The "crushing" condition source is not quoted in the spec, but the clamp itself is evidenced. | medium | Add to AP-06 an injectable `bool isCrushing` and `coef = max(coef, 0.2)` before `SetSpeedPercentage`, with one test; mark the condition source as a stub. Or state explicitly that C.4 is deferred to a named follow-up. |
| AP-04 | "Faster ability flag source" is attributed to T-020 (typed rules). `HasAbility(0)` is per-object veterancy state (FUN_0070d0d0, UNVERIFIED role), not a rules key; no task owning veterancy/abilities is named. | medium | Keep `HasFaster` as a plain bool input (already done) and name the dependency as "veterancy/abilities task (not yet defined)" rather than T-020. |
| AP-07 | `SpeedType=` (TechnoTypeClass+0x67C, spec data layout, ev_a607860c pseudocode) is needed as the table row selector and for the `SpeedType == 1` hill branch, but no package parses it and AP-07 does not name a dependency for it. | low | Add parsing of `SpeedType=` to AP-02 (same reader function FUN_00712170) or list it as an explicit T-020 dependency in AP-07. |
| AP-07 | Test "Unit, downhill, TrackedDownhill = 1.25 from table 0.8 -> 1.0": the spec caps only the table lookup at 1.0, not the post-hill product; a result of exactly 1.0 cannot tell whether an (invented) second cap was applied. | low | Use a factor giving a result > 1.0 (e.g. 1.0 table * 1.25 -> 1.25) to pin "no cap after hill factors". |
| AP-06 | `LeptonsPerStep = 7` bakes the UNVERIFIED unit reading ("leptons per frame", spec C inference) into a constant name, while the open points say "do not assert cell distances". The step size 7 itself is VERIFIED-by-tool-output; the unit is not. | low | Name it `StepBudget = 7` or `BudgetPerStep` with a `// unit (leptons) UNVERIFIED, T-022 C` comment. |
| AP-06 | Ordering test "`SetSpeedPercentage` is called before `GetCurrentSpeed` each frame": in the game `GetCurrentSpeed` (L190) is still called when the bool argument is set and only its result is masked (L194). The package's `skipSpeed ? 0 : GetCurrentSpeed()` short-circuits the call, so the ordering test is undefined for `skipSpeed = true`. Harmless for a pure getter but changes observable call sequence on a fake. | low | Either always call `GetCurrentSpeed()` and mask the result (mirrors L190/L194), or scope the ordering test to `skipSpeed = false`. |
| AP-01 | "Depends on: none (T-021 only for the project skeleton)": T-021 is the fixed tick / frame loop, not the project skeleton. Misattributed. | low | Drop the parenthetical or name the actual skeleton task. |
| AP-01 | "disallow `Math.FusedMultiplyAdd` and `float` intermediates by analyzer comment/test": a unit test cannot enforce an absence of FMA; only an analyzer rule or code review can. | low | Say "by review/analyzer rule" and remove "test". |
| AP-01 | Test `F2I(0.0) == 0` is attributed to "spec table B, rows 1-2"; the spec table has no 0 row. `HalveTowardZero(-7) == -3` and `(7) == 3` are derived (spec table only has 10 -> 5). Attributions are slightly over-stated but the values are correct (cdq/sub/sar gives -7 -> -3, 7 -> 3, 10 -> 5). | low | Label those three as "derived". |
| AP-03 | "parsed via T-005 double reader": the spec only says the loader reads the keys "into floats" (row 8) and lists FUN_005283d0 as an inferred double reader; which reader the country loader uses is not quoted. The float storage (+0x128/+0x12C/+0x130) is in the spec and the float-precision test is a fair derivation. | low | Word as "read as float (reader function not quoted in spec)". |
| AP-03 | Test "Missing key: assert the loader leaves the T-020 default" bakes an unknown default into a test; spec silent (acknowledged in open points). Also, owner -> country resolution (`Owner.Type`, HouseClass+0x34) has no test. | low | Make the missing-key test assert only "field unchanged from whatever it was before the read" (which is what an INI reader with a default of the current value does), and add one selector test that goes through an owner object. |
| AP-05 | The wrapper identity (FUN_00521d80 = InfantryClass::GetCurrentSpeed, vtable slot +0x538 -> 0x521D80) is listed in the spec under "Helper functions (roles inferred from use, UNVERIFIED)" and row 18 (UNVERIFIED). AP-05 marks only the constant as UNVERIFIED and presents "calls AP-04 then applies prone multiplier when prone" as settled; the "when prone" condition comes from the Phobos hook name only. | low | Add "wrapper role and prone condition inferred (spec helper list, row 18)" to Spec basis and tag the prone tests accordingly. |
| AP-04 | `SpeedMultiplier` default 1.0 and `SpeedPercentage` default 1.0: spec is silent on both initial values (only the setter path via Process is evidenced). AP-04 notes this for +0x580 but not for +0x578. | low | Add `SpeedPercentage` initial value to open points with the same "spec silent, default 1.0" note. |
| AP-07 | The spec is internally stale: Open questions still say "Decode `Process` (REA run pending)" while row 17 is VERIFIED-by-tool-output and Rule D quotes its pseudocode. AP-07 builds on D, which is fine, but the spec should be fixed before AP-07 is started so the basis is unambiguous. | low | Note in AP-07 that the spec's open question is stale and ask the spec owner to remove it. |
| AP-02 | No defects found. Recomputed all table-A values from the rule (clamp 0..100, `<<8 / 100` truncating, cap 255): -5 -> 0, 0 -> 0, 4 -> 10 (1024/100), 6 -> 15 (1536/100), 99 -> 253 (25344/100), 100 -> 255 (256 capped), 150 -> 255; `SETLE/DEC/AND` zeroing and `CMP 0x64/JL` clamp match the asm; `>= 255 -> 255` matches `CMP EDX,0xff / JL`. Dependencies T-005, T-020 stated. | - | - |

| AP-04 | Table-B values recomputed: 255 -> 255; 255*1.2 -> 306 (mode-independent in double, see AP-01 finding); 10*0.75 = 7.5 -> 8 under nearest (both tie rules), 7 under truncation (tagged, correct); 10 with flag -> 5; Faster 100*1.2 = 120.0 exactly in double -> 120 under any mode (tag not needed). | - | - |

## Project-rule check
- Deterministic / no wall clock / no rendering: no violation found in any package. All inputs are injected; frame advance is driven by T-021.
- Every rule has a test: C.4 (0.2 crush clamp) has none (see finding); owner -> country resolution in AP-03 has none; AP-04's `SetSpeedPercentage` mutable state is only tested indirectly through AP-06/AP-07 fakes.
- Session size: AP-04, AP-06, AP-07 are "medium" and each adds 2-3 source files plus stubs; acceptable. AP-06's `DriveLocomotor.cs` frame entry (LinkedTo wiring) is the most likely to grow beyond one session once the track-table step callback gets a real implementation; keep it a stub.
