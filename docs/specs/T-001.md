## Data layout

### MIX container (RA2/YR), file bytes (little-endian)

```
offset  bytes  type    field
0       2      uint16  format        ; 0x0000 => RA2/YR, non-zero => CnC
2       2      uint16  flags         ; bit0 (0x01) = unknown/unused, bit1 (0x02) = Blowfish-encrypted header
4       80     uint8[80]  keyblock   ; 80-byte RSA pre-image (present only when encrypted)
84      n      uint8[]   headerBlock; Blowfish ciphertext of the index (n = blockCount*8) when encrypted,
                             otherwise the plaintext index below
84+n    ...    uint8[]   file data   ; payloads referenced by index offsets
```

Index (header) plaintext, always:

```
offset  bytes  type    field
0       2      uint16  numFiles
2       4      uint32  dataSize      ; size of the file-data region
6       12     uint32[N]  fileId    ; little-endian
+4      4      uint32[N]  offset    ; offset into file (absolute, from byte 0)
+8      4      uint32[N]  size      ; payload length
```

`blockCount = (13 + 12*numFiles) / 8` 8-byte blocks (integer division, EV-001). This equals `ceil((6 + 12*numFiles)/8)` for the observed values — WDT (N=126): `(13+1512)/8 = 190` blocks = 1520 bytes, covering the 1518-byte index. Verified: decryption of all 4 real archives succeeded with this count.

### File ID hash (engine scheme)

**Canonical algorithm** (per user decision, based on EV-011/012/013): the engine computes the file ID as a CRC-32 over the **uppercased** filename, with a length-remainder prefix when the length is not a multiple of 4:

```
ComputeFileId(name):             # == OpenRA PackageEntry.HashFilename(name, CRC32)
    s = upper(name)
    L = len(s); r = L % 4
    if r != 0:
        lastgroup = s[L - r : L]                        # the incomplete trailing 4-byte group
        s = s + chr(r) + (r - 1) copies of lastgroup[0] # remainder byte, then repeats of the FIRST char of the LAST group
    return CRC32(s)              # standard zlib: poly 0xEDB88320, init 0xFFFFFFFF, xorout 0xFFFFFFFF
```

**CONFIRMED (EV-016).** The padding rule is **last-group-repeat**, not first-char-repeat. `LOCAL.MIX` (7 chars, r=3) pads to `LOCAL.M` + `\x03` + `L`+`L` → `LOCAL.M\x03LL` → CRC-32 = **0xA8548FD9**, which is **present** in the user's decrypted RA2.MIX index. The first-char-repeat alternative yields `0x9C208CF1`, which is **absent**. (The old vector `0x9C208CF1` in the table below was wrong.)
```

Evidence chain:
1. **EV-011** — the engine (`MixFileClass_Retrieve`, 0x5B40B0) builds the ID from `FUN_004A1DE0(upper(name), len)` on `CRC_00476D80`, i.e. a CRC engine, not a per-char rolling hash.
2. **EV-012** — YRpp's `CRC.h` gives the body of 0x4A1DE0: standard table CRC-32 with the length-remainder prefix above.
3. **EV-013** — OpenRA's `PackageHashType.CRC32` is a verbatim port of the same algorithm (same padding rule, same base CRC32), confirming the padding semantics are not an artifact.
4. **EV-015** — all 606 unique real IDs fall in [0x80000000, 0xEFFFFFFF], a range a per-char rolling hash of typical filename lengths cannot reach.

**Open ambiguity:** the alternative candidate OpenRA "Classic" (NUL-pad end + per-dword `rotl32+add`) also reaches the full range. Neither a positive RA2 name→ID match nor a counter-example distinguishes the two with the material available in this environment. The CRC-32 scheme is the one the engine source points at; Classic is the documented RA1/Tiberian-Dawn scheme and remains un-eliminated.

**Modding-Guide per-char scheme (EV-006/007):** reproduces its own 4 published vectors (FTNKNEXUS.VXL=0x00096814, FTNKNEXUS.HVA=0x000967CD, FTNKNEXUSTUR.VXL=0x004B4B04, FTNKNEXUSTUR.HVA=0x004B4ABD) and matches `create_mix.py`. It is **not** the engine scheme by the evidence above; treat it as the hash a modding tooling script produces, which may not be what the engine actually resolves.

## Rule

Given a MIX file:
1. Read `format` (u16) and `flags` (u16) at offset 0. `format != 0` → CnC variant (not exercised in this task, UNVERIFIED here).
2. If `flags & 0x02`: read the 80-byte keyblock at offset 4, derive the 56-byte Blowfish key via RSA (below), decrypt `blockCount` 8-byte blocks at offset 84 to recover the index plaintext. Otherwise the index plaintext starts at offset 4.
3. Parse `numFiles` (u16), `dataSize` (u32), then `numFiles` × {fileId u32, offset u32, size u32}.
4. The index is **not** guaranteed sorted (EV-010: RA2.MIX IDs are interleaved); expose a linear scan fileId → (offset, size).
5. Compute a filename's ID with the engine CRC-32 scheme above (EV-011/012/013) — this is how a lookup name is mapped to an index entry.
6. Expose payload bytes at `offset` for length `size` (payload content decoding is a separate task).

Blowfish key derivation (EV-003): modulus = 512-bit integer from base64 `AihRvNoIbTn85FZRYNZRcT+i6KpU+maCsEqr3Q5q+LDB5tH7Tz2qQ38V` (little-endian byte order as stored in reference); exponent e = 0x10001; `key = (keyblock^e mod n)`, first 56 bytes.

Cipher (EV-002, Westwood-modified Blowfish, NOT standard):
- Block I/O: read two little-endian dwords, **byte-swap each dword** before the cipher, byte-swap back after.
- `Round(a,b,p): a ^= F(b) ^ p`
- `F(b) = (S0[b]+S1[b]) ^ S2[b] + S3[b]` (all mod 2^32)
- `S(i,x) = lookupMfromS[i, (x >> (3 - (3-i))) & 0xFF]` — i.e. byte selection with the index expression `(x >> ((3-i)<<3)) & 0xFF`.
- 18 P-box values + 4×256 S-box values from the pi-constant tables in the reference.

## Pseudocode

```
ReadMixIndex(path):
    b = read(path); fmt = u16(b,0); flags = u16(b,2)
    if flags & 0x02:
        keyblock = b[4:84]
        key  = BlowfishKeyDerive(keyblock)          # 56 bytes, RSA public-op on 80-byte block
        dataStart = fileLength - dataSize            # dataSize is needed below; see note
        # header extent = the gap between the 84-byte keyblock end and the data region start,
        # rounded down to 8-byte blocks (see "Open questions: header extent")
        header = WwBlowfish(key).Encrypt(b[84 : dataStart])   # ECB; decrypt == encrypt
    else:
        header = b[4 : 4 + (6 + 12*N)]
    N = u16(header,0); dataSize = u32(header,2)
    entries = [ (u32(h,6+12i), u32(h,10+12i), u32(h,14+12i)) for i in 0..N )]
    return (N, dataSize, entries)
```

`WwBlowfish` block processing (from reference, EV-002):
```
Encrypt8(block8):
    a = swap_le(u32(block8,0)); c = swap_le(u32(block8,4))
    for i in 0..15: (c,a) = (a, Round(c,a,P[i]))
    (c,a) = (a, Round(c,a,P[16])); (c,a) = (a, Round(c,a,P[17]))
    return swap_le(c) ++ swap_le(a)
Round(x,y,p): x ^= F(y) ^ p; return x
F(y): (S(0,y)+S(1,y)) ^ S(2,y) + S(3,y)        # all mod 2^32
```
(The exact double-round ordering and `SwapBytes` placement must be taken verbatim from `refs/OpenRA/.../Blowfish.cs`; the reference is the authoritative cipher spec.)

## Open questions

- **File ID hash — engine scheme chosen, not yet positively confirmed against an RA2 name→ID pair.** The engine references (EV-011/012/013) point to the padded CRC-32 (YRpp `CRCEngine`), now the canonical algorithm per user decision. OpenRA "Classic" (dword rotl+add) is the un-eliminated alternative (also full-range). No RA2-local `mix database.dat` exists in `refs/` (the one present is Tiberian Sun, EV-014), the install has no `LOCAL.MIX`/`CACHE.MIX` and no loose assets, so a positive confirmation (one real name hitting one of the 606 dumped IDs) was not achievable in this environment. **To close definitively:** obtain an RA2 `local mix database.dat` (or any confirmed RA2 name→ID pair) and check it against the IDs in `allids.txt`.
- **`langmd.mix` / `marble.mix` dump failures.** Two of the 15 archives failed in the harness dump (error not yet inspected); possibly a different header layout or truncated files. Uninvestigated.
- **`flags` bit 0 (0x01).** Set in WDT/RA2/RA2MD (0x0003) but not MULTI (0x0002). Effect unknown (compression flag?). UNVERIFIED.
- **Header ciphertext extent vs. `dataSize`.** The encrypted region ends where file data begins, but file data is located by `dataSize` (inside the encrypted header). Empirically the plaintext index is 6+12N bytes and the ciphertext is `blockCount*8` bytes with `blockCount=(13+12N)/8`. Confirm the exact boundary rule (OpenRA uses `(13+12N)/8`; a trailing few bytes may be padding). All 4 real archives decrypt cleanly with this count.
- **CnC format** (thememd.mix / THEME.MIX, non-zero format field) is a different layout and is not covered here.
- **Payload compression** (the file data region is compressed in these archives) is a later task, out of T-001 scope.
